# Развёртывание 2.2

## Sites

Существующий project_id сохраняется в .openai/hosting.json. Manifest объявляет PNL_DB как D1 binding; R2 не используется. SQL и journal Drizzle находятся в drizzle. Sites применяет миграции при публикации. Предыдущие миграции неизменяемы.

Сборка: npm ci, npm test, npm run typecheck, npm run build. Исходники синхронизируются source helper Sites, который коммитит, отправляет точное состояние и пакует build. Публикуется archive из того же commit_sha. Существующая аудитория сохраняется.

В production не заданы Telegram secrets: GET /api/pnl/config возвращает ready:false. POST /api/pnl/requests и webhook возвращают 503 без сбора контактов. Это намеренное состояние до подключения менеджера.

## Обычный Node.js

PostgreSQL storage-этап реализован: настройки, аналитика и delivery имеют собственные Drizzle-адаптеры. Полный порядок — [docs/POSTGRESQL.md](docs/POSTGRESQL.md). Для постоянного сервера задать STORAGE_DRIVER=postgres, DATABASE_URL и SITE_ORIGIN, затем отдельно применить `npm run db:postgres:migrate` до startup. D1-миграции к PostgreSQL не относятся.

```sh
npm ci
npm run build:portable
npm run start:portable
```

Без конфигурации сохраняется demo. Next standalone содержит public и static благодаря scripts/prepare-standalone.mjs. Docker runner по умолчанию требует PostgreSQL, отдельный migrator запускает Drizzle Kit. Хранилище Telegram подключено, но реальная выдача требует конфигурации менеджера/бота. Админка Node закрыта до отдельной авторизации; публичный сбор аналитики от неё не зависит.

## Подключение менеджера позже

Не помещать секреты в .openai/hosting.json, Git, клиентские переменные NEXT_PUBLIC_* или URL. В Sites задать server-only environment через штатный инструмент; на другом хостинге — secret manager окружения. Имена:

- TELEGRAM_BOT_TOKEN
- TELEGRAM_WEBHOOK_SECRET
- Контакт менеджера и шаблон сообщения задаются в /admin, а не в env
- TELEGRAM_MANAGER_USER_ID
- TELEGRAM_BUSINESS_CONNECTION_ID
- PNL_PUBLIC_ORIGIN

Нужно подключить бизнес-бота к личному аккаунту менеджера с правом отвечать, установить webhook и настроить ежедневную очистку до реального сбора. Полный порядок и официальный API — docs/TELEGRAM.md. После настройки сервера включите «Принимать заявки на Excel» в /admin. Интерфейс включит форму только при корректной серверной конфигурации и включённой выдаче. Бот не отправляет обычные рекламные сообщения; выдача запускается только явным запросом пользователя.

## Локальная БД

После изменения db/schema.ts выполнить npm run db:generate и проверить сгенерированные миграции. Для preview применять SQL к локальной D1 стандартным Wrangler migrations apply с binding PNL_DB и migrations_dir=drizzle; production и local — отдельные базы. SQL не создаётся при HTTP-запросе. В тестах тот же SQL выполняется настоящим SQLite, а не только моками.

## Зависимости

package-lock.json обязателен. npm overrides обновляют uuid у ExcelJS до совместимого CommonJS-релиза 11.1.1+ (используется v4) и esbuild у @esbuild-kit/core-utils до исправленной 0.25.x. Эти ограничения — стандартные настройки npm, проверенные сборкой, генерацией миграций и тестами. Drizzle ORM обновлён до исправленной 0.45.4. Не использовать npm audit fix --force или замены API библиотек.

## Панель управления

Открыть /admin и войти через ChatGPT под аккаунтом владельца Sites. Перед первой публикацией задаются ADMIN_BOOTSTRAP_EMAIL (секрет, email единственного владельца из access policy Sites) и SITE_ORIGIN (точный HTTPS origin сайта). Первый владелец явно нажимает «Открыть панель управления»: POST закрепляет доверенный gateway subject в site_owner. GET не меняет БД. После привязки email больше не является правилом доступа; используется неизменяемый subject. Не подменяйте subject глобальным account_user_id Sites: это разные пространства ID. Для смены владельца нужен контролируемый операторский перенос после проверки права собственности, резервной копии и аудита; публичного endpoint смены нет.

Локально используйте штатный mockAuth стартера и игнорируемый .dev.vars с ADMIN_BOOTSTRAP_EMAIL=seedy@sites.test и SITE_ORIGIN=http://127.0.0.1:5173. Примените миграции к отдельной локальной D1. Эти значения не публикуются. Нет dev-пароля или bypass в приложении.

Настройки сохраняются в D1, секреты — только в окружении. Сохранение выполняет CAS по revision и записывает аудит изменённых разделов в одной транзакции. Конфликт 409 не перезаписывает чужие правки. Изменения применяются при следующей загрузке страницы/запросе без build/deploy. Обновление секретов окружения в Sites всё ещё требует новой публикации. Задача очистки контактов работает и при выключенной выдаче.

## Собственная аналитика 2.2

Дополнительных сервисов и секретов не требуется: существующие PNL_DB, SITE_ORIGIN и owner identity используются повторно. Sites применяет 0002 перед новой версией Worker; локальный preview требует отдельного migrations apply. Новых переменных NEXT_PUBLIC и внешних tracking endpoints нет. Калькулятор и доступ к настройкам не зависят от доступности коллектора.

Очистка analytics_sessions каскадно удаляет события небольшими порциями при ingest/report и не зависит от выключенного Telegram. Отчёт ограничен 90 днями; строгий purge при полном отсутствии трафика требует штатного планировщика на целевом хостинге (не создаётся автоматически). Не путать его с существующей политикой удаления контактов delivery. Резервные копии и edge quota для большого публичного трафика — ответственность эксплуатации.
