# Вход владельца на собственном сервере

Node.js использует Better Auth 1.7.27 с официальным Drizzle adapter и PostgreSQL. Sites сохраняет прежний вход через ChatGPT. Публичный калькулятор не требует аккаунта. Django, Google и почтовый сервис не нужны для этого варианта.

## Первичная настройка

1. Сделайте резервную копию и примените `npm run db:postgres:migrate` миграционной ролью. Новая миграция `0001_productive_captain_universe.sql` создаёт только auth-таблицы; старые PostgreSQL- и D1-миграции не изменены.
2. Установите runtime-переменные `STORAGE_DRIVER=postgres`, `DATABASE_URL`, `SITE_ORIGIN` и `BETTER_AUTH_SECRET`. `SITE_ORIGIN` должен быть точным публичным HTTPS origin. HTTP допускается только на локальном loopback для разработки.
3. Сгенерируйте секрет один раз и сохраните в secret manager сервера:

   ```sh
   node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
   ```

   Один и тот же секрет должен быть у всех реплик и сохраняться между выпусками. В Git и `NEXT_PUBLIC_*` его не помещать. Смена секрета аннулирует подписи cookies; для управляемого отзыва используйте команду ниже.

4. На доверенной операторской машине или в интерактивном контейнере `migrator` задайте **отдельный** `ADMIN_DATABASE_URL`. Команды доступны после `npm ci`; tsx и terminal prompts входят в образ migrator. Не передавайте эту переменную контейнеру runner.
5. Выполните `npm run admin:create`. Терминал запросит email, имя и пароль с подтверждением. Пароль 12–128 символов вводится скрыто и не принимается аргументом командной строки или переменной окружения. Используйте уникальный пароль из менеджера паролей.
6. Запустите приложение и откройте `/admin`. Войдите созданными данными. В `/admin/analytics` доступны отчёты; посещения вошедшего владельца исключаются из статистики.

Если `BETTER_AUTH_SECRET` отсутствует, публичные функции продолжают работать, а админка и `/api/auth/*` закрыты с 503. Пустой или короткий секрет останавливает startup с именем некорректного поля без его значения. Без применённой auth-схемы сервер с включённой авторизацией не запускается. Наличие readiness не подтверждает создание владельца — это отдельная операторская операция.

## Роли базы данных

В дополнение к правам из [POSTGRESQL.md](POSTGRESQL.md), роль приложения `coffee_app` получает:

```sql
GRANT SELECT ON auth_user, auth_account, auth_verification TO coffee_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON auth_session, auth_rate_limit TO coffee_app;
```

Роль для операторских команд, например `coffee_admin`, создаётся администратором PostgreSQL отдельно. Она не является superuser и не требует DDL:

```sql
GRANT CONNECT ON DATABASE coffee_market TO coffee_admin;
GRANT USAGE ON SCHEMA public TO coffee_admin;
GRANT SELECT, INSERT ON site_owner, auth_user, auth_audit TO coffee_admin;
GRANT SELECT, INSERT, UPDATE ON auth_account TO coffee_admin;
GRANT SELECT, DELETE ON auth_session TO coffee_admin;
```

Владелец схемы выдаёт эти права после миграций. Приложение не создаёт роли и не меняет права при startup. Runtime не имеет права создавать пользователей, менять пароль, назначать владельца или удалять журнал безопасности. Существующий `INSERT ON site_owner` из прежней конфигурации Node можно отозвать: `REVOKE INSERT ON site_owner FROM coffee_app;` — в Node владелец назначается только оператором. На Sites права управляются D1 отдельно.

## Сессии и защита

- Владелец определяется сохранённым `site_owner.subject`, равным ID пользователя Better Auth. Email не даёт роль. `ADMIN_BOOTSTRAP_EMAIL` на Node игнорируется. Заголовки `oai-authenticated-*` не используются.
- Пароли хеширует штатный scrypt Better Auth. Пользователь, credential account, назначение владельца и аудит создаются одной транзакцией. Повторный `admin:create` не перезаписывает владельца.
- Сессия хранится в PostgreSQL и действует 8 часов без автоматического продления. Cookie подписана, HttpOnly, SameSite=Lax и Secure на HTTPS. Домен cookie не расширяется на соседние поддомены. Клиентский cookie cache отключён: удалённая/просроченная сессия перестаёт давать доступ при следующем запросе.
- HTTP доступны только `POST /api/auth/sign-in/email`, `POST /api/auth/sign-out` и `GET /api/auth/get-session`. Регистрация, смена email/пароля, удаление аккаунта и восстановление по email закрыты. Нет пароля по умолчанию, bootstrap по первому посетителю или обхода в development.
- Мутации auth требуют точный Origin и application/json. GET не выполняет logout. Тело ограничено 8 KiB; валидацию credentials выполняет библиотека. Настройки по-прежнему требуют владельца, Origin, административный header и CAS revision.
- Лимиты Better Auth сохраняются атомарно в БД: 5 попыток входа за 60 секунд, общий лимит 60 запросов за 60 секунд для остальных разрешённых операций. Чтение сессии не расходует лимит. Пока trusted proxy не подключён, все посетители разделяют один счётчик для каждого endpoint. Поддельные IP-заголовки его не обходят; нагрузка может временно мешать входу владельца, поэтому reverse proxy также должен ограничивать трафик на `/api/auth/`.
- Endpoint не разрешает произвольные callback-адреса из формы. После входа UI открывает только `/admin` или `/admin/analytics`. Каждый административный API заново проверяет сессию и закреплённого владельца.

## Восстановление доступа

На доверенной машине с `ADMIN_DATABASE_URL`:

```sh
npm run admin:reset-password
npm run admin:revoke-sessions
```

Первая команда запрашивает существующий email владельца и новый пароль. Она меняет credential hash, отзывает **все** его сессии и записывает `password_reset` в одной транзакции. Вторая завершает все сессии без смены пароля. Ошибка аудита откатывает изменение. Login и операторские команды используют одну PostgreSQL advisory lock: вход с прежним паролем, начавшийся одновременно со сменой, не оставляет действующую сессию после успешного reset.

Не удаляйте `site_owner` для восстановления. Смена владельца/его email — отдельная контролируемая операция после проверки права владения и резервного копирования; публичного интерфейса для неё нет. Если в PostgreSQL уже импортирован старый Sites owner subject, автоматическая привязка по email запрещена: нужен отдельный проверенный перенос владельца.

## Эксплуатация и проверка

Auth-таблицы включаются в резервную копию вместе с настройками. Сессии содержат чувствительные токены: ограничьте доступ к backup. Журнал `auth_audit` содержит только ID, действие и время, без паролей и токенов. При восстановлении старой БД отзовите восстановленные сессии. Просроченные сессии доступа не дают, но плановая очистка `auth_session WHERE expires_at < now()` и `auth_verification WHERE expires_at < now()` должна выполняться оператором/планировщиком с нужными правами. Rate-limit строки очищает библиотека при работе лимитера. Не удаляйте актуальные счётчики для обхода блокировки.

Интеграционные тесты запускают настоящий Next standalone, проверяют вход, защищённые страницы/API, исключение владельца из аналитики, сохранение сессии после рестарта и logout. На настоящем PostgreSQL дополнительно проверяются конкурирующая активация, независимые пулы, подмена cookies/identity, expiry, конкурентный rate limit, reset/revocation и откат при ошибке аудита. UI-тесты проверяют форму, состояние ожидания, generic ошибки и повтор после сбоя. Миграции применяются только release-job, не процессом приложения.

Официальные контракты: [Better Auth / Drizzle](https://better-auth.com/docs/adapters/drizzle), [email/password](https://better-auth.com/docs/authentication/email-password), [sessions](https://better-auth.com/docs/concepts/session-management), [rate limits и доверие IP](https://better-auth.com/docs/concepts/rate-limit).
