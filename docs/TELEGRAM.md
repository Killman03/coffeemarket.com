# Автоматическая выдача P&L через личный чат менеджера

## Реальный механизм

Используется официальный Telegram Business Bot API. Пользователь открывает **личный чат менеджера**, видит подготовленный текст и сам нажимает «Отправить». Подключённый к этому аккаунту бизнес-бот получает `business_message`, формирует Excel на 3 месяца и отправляет документ от имени бизнес-аккаунта через `sendDocument` с `business_connection_id`. В подписи явно указано, что файл сформирован автоматически; обычную переписку продолжает менеджер.

Обычный Bot API не может отправлять сообщения от имени произвольного личного аккаунта. Не используются пользовательские сессии Telegram, MTProto-скрипты, cookies, эмуляция человека или доступ к чужим аккаунтам. Для автоматической выдачи менеджер должен подключить бота в настройках Telegram Business и разрешить ответы в нужных чатах. Условия доступности Telegram Business проверяются при настройке аккаунта.

Официальные источники: [Business Bots](https://core.telegram.org/bots/features#business-bots), [BusinessConnection](https://core.telegram.org/bots/api#businessconnection), [sendDocument](https://core.telegram.org/bots/api#senddocument), [ссылки на пользователя с готовым текстом](https://core.telegram.org/api/links#public-username-links).

## Состояние по умолчанию

Без полного набора настроек `GET /api/pnl/config` возвращает `ready: false`, POST возвращает 503, интерфейс не собирает телефон. Калькулятор продолжает работать бесплатно. Наличие кода интеграции не означает, что аккаунт менеджера или бот уже подключены.

В этом репозитории нет токенов, номера реального менеджера, webhook secret или реальных заявок. Настройка webhook и подключение бота к бизнес-аккаунту выполняются владельцем аккаунта при вводе интеграции в эксплуатацию. Тесты используют изолированные подмены Telegram и SQLite.

## Настройки сервера

| Переменная / binding              | Назначение                                                        |
| --------------------------------- | ----------------------------------------------------------------- |
| `PNL_DB`                          | Постоянная база D1 с применёнными миграциями `drizzle/`           |
| `PNL_PUBLIC_ORIGIN`               | Точный HTTPS origin сайта, без завершающего `/`                   |
| `TELEGRAM_BOT_TOKEN`              | Секрет токена подключённого бизнес-бота                           |
| `TELEGRAM_WEBHOOK_SECRET`         | Независимый случайный секрет из 32–256 символов `A-Z a-z 0-9 _ -` |
| `TELEGRAM_BUSINESS_CONNECTION_ID` | Идентификатор подключения именно аккаунта менеджера               |
| `TELEGRAM_MANAGER_USER_ID`        | Числовой Telegram ID владельца бизнес-аккаунта                    |

В /admin укажите хотя бы один адрес менеджера: username или международный телефон. Если есть оба, используется username. Для ссылки по телефону настройки приватности менеджера должны разрешать поиск по этому номеру. Это адрес менеджера; телефон в форме — отдельный контакт клиента.

Не передавайте секреты через `NEXT_PUBLIC_*`, Git, HTML или браузерный JavaScript. В Cloudflare задавайте их через управляемые server-side secrets; на другом хостинге используйте его секретное хранилище.

Webhook: `POST https://<ваш-домен>/api/telegram/webhook`. При регистрации через `setWebhook` передайте тот же `secret_token` и разрешите `business_message` в `allowed_updates`. Секрет проверяется по `X-Telegram-Bot-Api-Secret-Token` до разбора тела. Не логируйте Bot API URL с токеном, тела запросов, телефоны и расчёты; отключите захват этих данных внешними HTTP/APM-прокси.

## Контракт и согласие

`POST /api/pnl/requests` принимает JSON `{input, context: {market, currency}, phone, consent: true}`. Валидируются общая расчётная схема, допустимый рынок/валюта и международный телефон через `libphonenumber-js/max`. Этот номер **введён пользователем, а не подтверждён Telegram или SMS**. Не следует считать его проверенным номером владельца чата.

Перед отправкой формы пользователь видит цель обработки и отдельно отмечает согласие. Сервер сохраняет точный текст согласия, его версию и время вместе с заявкой. Это согласие на сохранение заявки и выдачу файла, не на рекламу и звонки. Правовой текст и сведения об операторе данных следует утвердить перед реальным сбором контактов для выбранных рынков.

Ответ: `{telegramUrl, expiresAt}`. Ссылка содержит только случайный 192-битный билет и заранее подготовленный текст. Телефона, рецептур и финансовых значений в URL нет. В базе хранится SHA-256 билета. Ссылка действует 15 минут и атомарно привязывается к одному Telegram-пользователю. Человек должен отправить подготовленное сообщение в течение этого срока. Если изменён служебный код или сообщение не отправлено, файл не выдаётся; обычные сообщения не запускают автоматические ответы.

Сервер принимает триггер только из личного входящего `business_message` настроенного подключения. Исходящие сообщения менеджера, сообщения ботов, изменения сообщений и остальные события игнорируются. Перед выдачей `getBusinessConnection` проверяет владельца, активность подключения и право `can_reply`. Автоматическая отправка выполняется в ответ на входящее сообщение клиента, с учётом 24-часового окна Telegram.

## Хранение, защита от повторов и ограничения

- В таблице `pnl_requests` сохраняются расчёт, контекст, заявленный телефон, согласие и минимальные Telegram ID. Параметры SQL передаются через prepared statements.
- Максимальное JSON-тело заявки — 16 KiB, webhook — 64 KiB, включая потоковую передачу без `Content-Length`. Проверяется точный `Origin` формы; это защита от запросов чужих браузерных страниц, не авторизация и не защита от скриптов.
- Создание ограничено пятью заявками за 10 минут на хешированный адрес клиента и 100 заявками в минуту суммарно. В Cloudflare используется доверенный `CF-Connecting-IP`. Другой хост должен подставлять проверенный адрес клиента в адаптере и удалять входящий поддельный заголовок; без него применяется общий лимит `anonymous`. Для большого публичного трафика добавьте edge rate limits перед API.
- `update_id` дедуплицируется постоянно в БД. Состояние выдачи захватывается compare-and-set SQL, поэтому параллельные события не отправляют два документа.
- Ошибка генерации или явно отклонённый Bot API запрос допускает повтор webhook. При неопределённом сетевом исходе `sendDocument` заявка становится `unknown`, автоматическая повторная отправка отключается. Bot API не предоставляет ключ идемпотентности для `sendDocument`; гарантия exactly-once была бы недостоверной. Менеджер проверяет чат и при необходимости создаёт новую заявку.
- При аварийной остановке процесса `processing`/`sending` требуют операционной проверки; автоматический сброс мог бы отправить дубликат. Для восстановления сначала проверьте чат, затем установите известное состояние заявки и обновления. Не повторяйте отправку вслепую.
- Контакты и расчёты удаляются по 30-дневной границе; служебные update ID — через 7 дней. `repository.cleanup(now)` вызывается при входящих запросах. **До включения реального сбора настройте ежедневную плановую очистку**, чтобы удаление выполнялось и при отсутствии трафика. Для строгого срока задайте задаче период и границу в соответствии с утверждённой политикой; удаление из резервных копий также регулируется политикой хостинга. Не включайте сбор до подготовки этой операции.

SQL для плановой очистки (время — Unix milliseconds):

```sql
DELETE FROM pnl_requests WHERE created_at < (unixepoch() * 1000 - 30 * 86400000);
DELETE FROM pnl_updates WHERE created_at < (unixepoch() * 1000 - 7 * 86400000);
```

Вместо прямого SQL планировщик может вызывать `POST /api/pnl/cleanup` с `X-Telegram-Bot-Api-Secret-Token`, равным webhook secret. Endpoint не принимает дату/условие удаления из запроса: границы 30 и 7 дней задаёт сервер. Без секрета возвращается 401, ответ не содержит телефоны или расчёты. Настройте ежедневный вызов и мониторинг его ошибок до включения сбора. Сам планировщик автоматически не создаётся. Публичное согласие не обещает автоматического удаления в конкретный срок до настройки этой операции.

Доступ к БД с контактами должен быть ограничен сотрудниками, которым он нужен. Публичного endpoint списка заявок нет. Для удаления по обращению используйте административный доступ к хранилищу; не добавляйте незащищённый API выгрузки контактов.

## Переносимость

`src/server/contracts.ts` задаёт порт DeliveryRepository. src/server/delivery.ts не зависит от Cloudflare, src/server/telegram.ts использует стандартные fetch/FormData/Bot API. D1-адаптер связывается с request-scoped runtime в sites-runtime.ts, PostgreSQL-адаптер — с процессным Node runtime при startup. Общий runtime.ts работает с портами.

Для Node PostgreSQL repository и composition root уже реализованы; запуск — [POSTGRESQL.md](POSTGRESQL.md). Нужны отдельные реквизиты менеджера/бота, авторизация и эксплуатационная настройка перед реальной выдачей. В Django тот же сценарий можно реализовать средствами монолита. Глобальный Map и локальный JSON не заменяют постоянную БД.

Excel формируется общим `createPnlWorkbook` из проверенного шаблона `public/templates/coffee-market-pnl-3-months.xlsx`. Входящая заявка не задаёт URL шаблона. Сервер загружает его только с настроенного origin, без redirects и с лимитом размера. Изменения шаблона проверяются workbook-тестами перед выпуском.

## Проверка перед включением

Примените сгенерированные миграции, настройте секреты и ежедневную очистку, подключите бота к нужному аккаунту и зарегистрируйте webhook. Проверьте выдачу на контролируемом тестовом клиенте с собственными данными: правильный чат менеджера, добровольная отправка текста, файл на 3 месяца, повтор webhook без дубля, истёкшая ссылка, отключённое подключение и отсутствие секретов/контактов в логах. Автотесты не проверяют реальные права вашего Telegram-аккаунта.

## Изменение контакта без публикации

Username, телефон, включение выдачи и шаблон сообщения хранятся в site_settings и меняются в /admin. Старые env TELEGRAM_MANAGER_USERNAME/TELEGRAM_MANAGER_PHONE больше не используются. Шаблон содержит ровно один {code}; необязательные {market}/{currency} подставляются общим helper. Обработчик распознаёт единственный фиксированный CM_<непрозрачный код>, поэтому уже созданные ссылки работают после изменения формулировки. Несколько кодов или неверный формат не запускают выдачу. Проверка аккаунта/Business connection и срока действия остаётся обязательной.
