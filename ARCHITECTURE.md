# Coffee Market: архитектура и расчётная модель

## Назначение и границы

Калькулятор себестоимости и потенциальной месячной прибыли для одного напитка.
Это сценарная модель: объём продаж и расходы задаёт пользователь. Она не
прогнозирует спрос по историческим продажам и не является бухгалтерской системой.
Валюта — KGS (сом), бизнес-часовой пояс — Asia/Bishkek.

## Слои и зависимости

```text
app/page.tsx                  composition root: выбирает репозиторий
  ├─ infrastructure          чтение каталога, сохранение в браузере
  │    └─ application/domain
  └─ presentation            React, форма, визуализация
       └─ application        сценарии, версия формата импорта
            └─ domain        схемы Zod, чистые формулы Decimal.js
```

- `src/domain/calculator.ts`: единственная реализация денежных формул.
  Не импортирует React, браузер, Worker, Sites, ORM или сетевые клиенты.
- `src/domain/catalog.ts`: контракт публичного каталога и порт
  `CatalogRepository`, преобразование известной фасовки в цену за кг.
- `src/application/scenarios.ts`: примерные значения, пресеты, сравнение спроса,
  версия переносимого JSON. Каждый сценарий вызывает то же расчётное ядро.
- `src/infrastructure/catalog-repository.ts`: снимок каталога через MCP,
  проверяемый общей схемой. Не содержит токенов и клиентских данных CRM.
- `src/infrastructure/scenario-storage.ts`: адаптер Web Storage с инъекцией
  хранилища; ошибки записи и повреждённые данные обрабатываются интерфейсом.
- `src/presentation`: доступные поля React Hook Form + Zod resolver, результаты,
  стандартный график Recharts и форматирование `Intl.NumberFormat`.
- `app`, `worker`, `vite.config.ts`, `scripts`: запуск и развёртывание.
  `worker` и vendored Sites scripts — адаптер текущего хостинга, их нет в ядре.

Формулы не копируются в компоненты, таблицу сценариев или график. На границе
расчётного ядра входные данные проверяются повторно, независимо от формы.
Пустое/нечисловое поле не становится нулём; результаты скрываются до исправления.

## Формулы

Для порции: `coffee = coffeePricePerKg × grams / 1000`,
`milk = milkPricePerL × ml / 1000`, сироп аналогично.

`ingredientsWithLoss = (coffee + milk + syrup) / (1 - lossPercent / 100)`.
Потери — доля закупленного сырья, которая теряется. Они не умножают упаковку.
`productionCost = ingredientsWithLoss + packaging + otherPerCup`.

`fee = salePrice × feePercent / 100`.
`tax = salePrice × turnoverTaxPercent / 100`.
Заданный налог моделируется как процент выручки, без встроенной налоговой ставки,
НДС, льгот или расчёта налога на прибыль. Нужную ставку и остальные расходы
пользователь вносит сам.

`variableCost = productionCost + fee + tax`.
`contribution = salePrice - variableCost`.
`contributionMarginPercent = contribution / salePrice × 100`.
`markupPercent = (salePrice - productionCost) / productionCost × 100`.
Маржинальность и наценка имеют разные знаменатели и не подменяют друг друга.

`volume = cupsPerDay × daysPerMonth`.
`fixedCosts = rent + salaries + utilities + otherFixed`.
`revenue = salePrice × volume`.
`profit = contribution × volume - fixedCosts`.
`fullCostPerCup = variableCost + fixedCosts / volume`.

`breakEvenCups = ceil(fixedCosts / contribution)`.
`breakEvenPerDay = ceil(breakEvenCups / daysPerMonth)`.
При `contribution <= 0` точка безубыточности — `null`, интерфейс показывает
недостижимость. При нулевых продажах сохраняется убыток на сумму постоянных
расходов; полная себестоимость на чашку — `null`. Нулевые знаменатели для
маржинальности/наценки тоже дают `null`, а не Infinity или NaN.

Все денежные операции выполняет Decimal.js, precision 32, ROUND_HALF_UP.
Входные числа ограничены схемой. Промежуточные суммы не округляются; месячные
суммы считаются по полной точности, отображаемые суммы округляются до 0,01 сом.
Из-за округления отображаемые строки могут отличаться от итога на 0,01 сом.
Целые чашки и дни проверяются Zod. JSON содержит входные параметры и версию,
вычисленные результаты при импорте игнорируются и пересчитываются заново.

## Данные CoffeeMarket и обновление

`catalog.snapshot.json` содержит шесть выбранных позиций из публичного каталога,
полученных инструментом `get_business_context` через подключённый CoffeeMarket
MCP 09.11.2026. Дата фактического получения (`fetchedAt`) и изменения каждой
карточки (`updatedAt`) хранятся отдельно. Снимок — не live-подключение сайта к MCP.
Цены розничные, поэтому не выдаются за закупочные цены владельца кофейни.
Фасовки 1000/250 г явно заданы после проверки названий, ручного парсинга названий нет.
Нулевой остаток сохранён и обозначен; его нельзя интерпретировать как наличие.
Наличие не ограничивает моделирование: можно рассчитать и отсутствующий товар.

Для обновления снимка: получить каталог авторизованным MCP-инструментом,
отобрать публичные кофейные позиции, привести поля к `catalogSchema`, явно
проверить фасовку, обновить дату, выполнить тесты и пересобрать сайт. Не копировать
CRM, company_reference, переписки, ключи или полный ответ инструмента в сборку.

Для автоматического обновления на coffeemarket.kg разработчик заменяет адаптер
снимка на репозиторий собственного каталога. При асинхронном доступе порт и
`app/page.tsx` переводятся на `Promise<Catalog>`/`await`; расчётное ядро и
компоненты результатов остаются прежними. Секреты MCP или внутреннего API
хранятся только на сервере. Нужны таймаут запроса, проверка `catalogSchema`,
явная дата свежести и сохранённый проверенный снимок при недоступности источника.
Это будущая интеграция, в текущем прототипе она не реализована.

## Перенос и сопровождение

Приложение использует React и стандартный App Router. Sites развёртывает его
через Vinext и Worker. Для независимого хостинга предусмотрен стандартный Next.js
build/start и Dockerfile. Подробные команды — `DEPLOYMENT.md`.
Формулы, сценарии и каталог также можно перенести в отдельный React-модуль
существующего сайта. Python не используется, корректировки путей импорта отсутствуют.

Сохранение — локальное, один сценарий на origin браузера. Оно не синхронизируется
между устройствами или доменами; при переносе используйте экспорт/импорт JSON.
Приложению не нужны база, внешние шрифты, аналитика, файлы cookie или CRM-доступ.
Защиту приватного адреса прототипа обеспечивает Sites на уровне хостинга.

## Проверки

Vitest: независимо посчитанный пример, отсутствие промежуточного округления,
нулевые продажи, отрицательная прибыль, невозможная безубыточность, нулевые
знаменатели, границы входных значений, сохранение/повреждение данных, смена
рецепта, конвертация фасовки и мгновенный пересчёт UI.
В тестах UI график заменён заглушкой; его визуализация проверяется в браузере.
Обязательный проход: `npm test`, `npm run typecheck`, `npm run build`.
Проверки и ограничения конкретной сдачи фиксируются в `VALIDATION.md`.

В менеджере пакетов задан стандартный patch override fflate 0.7.5: он исправляет
известную уязвимость версии 0.7.4, закреплённой транзитивной зависимостью
генератора OG-изображений. Это часть lockfile, а не изменение node_modules.
График загружается отдельным React.lazy-модулем; основные результаты доступны
до загрузки библиотеки графиков. Next.js использует отдельный каталог сборки
.next-node, чтобы не смешивать его артефакты с адаптером Sites.

## UI и встраивание, версия 1.1.0

Calculator — независимый компонент без магазинной навигации и футера.
StorefrontPreview содержит только контекст самостоятельной страницы.
Calculator.module.css изолирует имена классов и ограничивает reset корнем
компонента; глобального Tailwind preflight в виджете нет. Адаптация по ширине
контейнера реализована стандартными CSS container queries. Внешние токены
--cmc-* наследуются от контейнера, внутренние --_cmc-* содержат fallback.

src/widget/index.tsx предоставляет mountCoffeeCalculator и cleanup через
стандартный createRoot React. vite.widget.config.ts собирает независимые ESM
и CSS, без Worker/Sites/Next runtime. Тот же Calculator используется всеми
способами размещения; копий формы или денежных формул нет. Идентификаторы
полей создаются useId; JS-монтирования имеют собственный identifierPrefix.

Точки подключения, параметры и пример HTML описаны в INTEGRATION.md.
